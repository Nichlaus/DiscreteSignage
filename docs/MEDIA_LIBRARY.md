# Media library intake

Implemented locally; not deployed. The live system remains the settings release.
This milestone accepts quarantined uploads and lists their status. It does not
publish media, create thumbnails, transcode, schedule, or play files on screens.

## Upload contract

Owners with verified accounts, App Check and an active screens trial call
`beginMediaUpload` with exactly `businessId`, `requestId`, `name`, `contentType`
and `size`. The backend reserves a deterministic object path and counts both
bytes and slots transactionally. Concurrent retries cannot multiply reservations.

Initial allowances: 100 reservations and 1 GiB per business, JPEG/PNG/WebP up to
20 MiB, MP4/WebM up to 100 MiB, minimum 12 bytes. Reservations expire after at
most 30 minutes and never outlive the current trial.

Storage rules permit only the reserving verified owner to create the exact
object with its reserved byte count, MIME type and reservation metadata.
Expired/missing reservations, replacement, deletion, reads and listings are denied.
Membership revocation is checked against Firestore on upload. No device, staff
or manager can upload. Media metadata stays backend-only in Firestore.

`completeMediaUpload` takes `businessId` and `mediaId`. It checks current ownership
before inspecting server object metadata and the first 32 bytes of the exact
object generation. It rechecks ownership and trial in the completion transaction.
Matching files become `uploaded`; mismatches become `rejected`. Completion is
idempotent and audited. `listMedia` returns the owner's first 100 entries without
object paths, generations or download links.

Signature checks are preliminary format checks, not complete decoding, malware
scanning or codec validation. For example, an EBML signature alone does not prove
WebM compatibility. Uploaded files remain quarantined and never become playable
through this operation. The portal explicitly says playback validation is pending.
No public URL is generated by application code.

## Recovery and release gates

Validation: 36 emulator tests and the production build pass. The suite includes
owner isolation, strict upload metadata, expired reservations, overwrite denial,
quarantined read denial, concurrent quota reservation and signature mismatch.

- A finished object can be confirmed again if the completion response was lost.
- Abandoned, expired and rejected reservations retain their quota. Do not reset
  quota counters while their objects still exist: implement generation-safe
  cleanup and transactional quota release before production rollout.
- Provision/verify a Sydney Firebase Storage bucket and its exact name. This
  implementation targets `discretesignage.firebasestorage.app`; the bucket has
  not been provisioned or verified by this milestone.
- Grant the runtime read-only object access on that bucket for completion.
  Configure the Storage rules service's cross-service Firestore access.
- Enforce Storage App Check and deploy the reviewed Storage rules; add the three
  media callables and bucket protections to live postflight checks.
- Verify a real resumable upload and confirmation against the deployed bucket.
  Emulator completion tests use controlled storage responses, while Storage rules
  tests exercise real emulator uploads and cross-service reservation checks.
- Verify Firebase-generated download-token behaviour on the real upload response;
  remove bearer download tokens before any validated media delivery. Denied
  client SDK reads do not by themselves revoke a separately issued bearer URL.
- Full media decoding/limits, sanitized derivatives and authenticated delivery
  must precede playback. Preserve original quality; avoid needless re-encoding.
- Native Android integration, playlists and transitions are separate milestones.

Reference: [Storage rules conditions and Firestore access](https://firebase.google.com/docs/storage/security/rules-conditions).
